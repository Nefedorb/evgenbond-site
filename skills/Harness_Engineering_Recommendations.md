# Harness Engineering Recommendations
> Руководство для кодового агента. Читай перед началом любой задачи.

---

## 1. Принцип работы: Люди управляют, агенты исполняют

- Ты получаешь задачу через prompt — **не ждёшь** уточнений, если всё необходимое есть в репозитории.
- Если чего-то не хватает (инструмент, абстракция, документация) — **сигнализируй об этом явно**, не пытайся угадать или обойти.
- Никогда не пиши код «на авось» (YOLO-style): либо валидируй данные на границе, либо доверяй типизированному SDK.

---

## 2. Управление контекстом (Context Management)

**AGENTS.md — это карта, не энциклопедия.**

- Начинай с `AGENTS.md` (~100 строк), он даёт точки входа.
- Глубокий контекст ищи в `docs/`: design-docs, exec-plans, product-specs, references.
- Всё, чего нет в репозитории (Google Docs, Slack, устные договорённости) — для тебя **не существует**. Если нужна информация — проси перенести её в `docs/`.

```
AGENTS.md          ← точка входа, ~100 строк
ARCHITECTURE.md    ← карта доменов и слоёв
docs/
  design-docs/     ← design decisions + core-beliefs
  exec-plans/      ← active / completed / tech-debt-tracker
  product-specs/   ← требования к продукту
  references/      ← llms.txt справочники по зависимостям
  QUALITY_SCORE.md ← текущее состояние качества по доменам
  RELIABILITY.md
  SECURITY.md
```

## 3. Архитектурные ограничения (Architectural Invariants)

Внутри каждого домена зависимости строго однонаправлены:

```
Types → Config → Repo → Service → Runtime → UI
```

Сквозные аспекты (auth, connectors, telemetry, feature flags) — **только через `Providers`**.

**Правила:**
- Нарушение направления зависимостей → **запрещено**, даже если кажется удобным.
- Проверяй через custom linters перед открытием PR.
- Если linter выдаёт ошибку — читай сообщение целиком: в нём встроена инструкция по исправлению.

---

## 4. Цикл выполнения задачи (Execution Loop)

Для каждой задачи выполняй последовательно:

1. **Проверь** текущее состояние кодовой базы (читай релевантные `docs/`, схемы, тесты).
2. **Воспроизведи** баг или опиши acceptance criteria перед реализацией.
3. **Реализуй** изменение в изолированном `git worktree`.
4. **Верифицируй** локально: запусти приложение, прогони тесты, проверь логи (`LogQL`) и метрики (`PromQL`).
5. **Открой PR** с описанием: что сделано, как проверено, какие решения приняты.
6. **Отвечай на feedback** (от агента и человека) в том же PR — до одобрения всех reviewers.
7. **Эскалируй** человеку только если требуется суждение, выходящее за рамки технического.

---

## 5. Observability как инструмент верификации

Локальный стек observability доступен в каждом worktree:

| Сигнал | Query language | Применение |
|--------|---------------|------------|
| Logs   | LogQL         | отладка, проверка поведения |
| Metrics | PromQL       | SLA проверки (напр. startup < 800ms) |
| Traces | TraceQL       | корреляция между сервисами |

- Перед закрытием задачи убедись, что критические user journeys **не превышают** установленных порогов.
- Используй скриншоты и DOM-снимки (Chrome DevTools MCP) для верификации UI-изменений.

---

## 6. Управление знаниями (Knowledge Management)

- Архитектурные решения, принятые в процессе работы → фиксируй в `docs/exec-plans/active/`.
- После завершения задачи → перемещай план в `docs/exec-plans/completed/`.
- Если обнаружил техдолг → добавляй запись в `docs/exec-plans/tech-debt-tracker.md`.
- Документация — это **living artifact**: если код расходится с docs/, обновляй docs/ в том же PR.

---

## 7. Выбор зависимостей (Dependency Selection)

**Предпочитай "boring tech"** — технологии со стабильным API и хорошим представлением в обучающих данных.

- Если поведение upstream-библиотеки неочевидно — **реализуй минимальное подмножество** внутри репозитория с полным test coverage и интеграцией с OpenTelemetry.
- Пример: вместо `p-limit` → собственный `map-with-concurrency` хелпер, полностью типизированный и покрытый тестами.
- Все утилиты → в общий `utils/`-пакет, не дублировать в каждом домене.

---

## 8. Качество и линтинг (Quality Gates)

Обязательные проверки перед merge:

- [ ] Custom linters: направления зависимостей, соглашения об именовании схем/типов, размер файлов.
- [ ] Structured logging (без `console.log` в продуктовом коде).
- [ ] Границы данных валидируются на входе (Zod или аналог) — не внутри бизнес-логики.
- [ ] Новый код покрыт тестами; критические пути — 100%.
- [ ] `docs/` обновлена, если изменилось поведение.

Нестабильный тест (`flaky test`) → **не блокирует** merge при повторном прогоне, но требует отдельного тикета в tech-debt-tracker.

---

## 9. Энтропия и рефакторинг (Entropy Control)

- Если видишь паттерн, который нарушает «золотые принципы» (Golden Principles) репозитория — открывай **отдельный точечный PR** на рефакторинг, не смешивай с feature-работой.
- Не воспроизводи неоптимальные паттерны только потому, что они уже есть в кодовой базе.
- При обнаружении устаревшей документации — открывай PR на обновление (doc-gardening).

---

## 10. Эскалация (Escalation Protocol)

Передавай задачу человеку, если:

- Требуется продуктовое решение (что строить, а не как).
- Архитектурное изменение затрагивает более одного домена и не покрыто существующими exec-plans.
- После 3 итераций цикла проблема не решена.
- Linter или CI падают по причине, которую невозможно устранить без изменения самих правил.

В остальных случаях — **решай самостоятельно** и документируй принятое решение.
